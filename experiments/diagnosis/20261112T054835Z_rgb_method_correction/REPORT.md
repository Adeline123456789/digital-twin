## 已解决的具体软件问题

既有导出器以 external RGB 为主时间轴，另存每个选中相机帧自己的曝光时间。两个观测脚本直接拿主时间轴标注右腕图像，混淆了不同相机的拍摄时刻。修正为：

`右腕单调时间 = 主单调时间 + 右腕曝光 Unix 时间 - 主 Unix 时间`

共享函数 `observe_real_failures.camera_monotonic_times()` 已接入 `observe_real_failures.py` 和 `validate_rgb_motion.py`。后者按修正时间查询阶段并插值夹爪反馈。HDF5 内原来按主时间轴采样的关节数组仍保持其原语义；没有把它们假称为曝光时刻的新测量。修正不改变图像顺序、原始数据、运动控制、成功检测器或物理参数。

只读核验逐帧比较原 RGB 元数据的 source_frame 与曝光时间，三条记录全部一致；回归测试覆盖曝光跨越命令边界的情况。全套 **28 项软件测试通过**。

| 已有记录 | 帧数 | 右腕与主时间差范围，ms | 查询命令行改变 | 阶段标签改变 |
|---|---:|---:|---:|---:|
| residual | 1,882 | -16.675 / +16.672 | 1,752 | 6 |
| grip_hold | 1,868 | -8.141 / +9.889 | 836 | 0 |
| smooth | 1,584 | -16.636 / +16.627 | 471 | 0 |

residual 的零起始帧 677 从 descend 修正为 grasp，768 从 lift 修正为 grasp，839 从 transport 修正为 lift，其余变化见 result.json。命令行改变不代表同样数量的动作内容改变。原第六轮数值使用旧时序；本次没有重跑跟踪或重算其测量门槛，不能把修正后的软件冒称为修正后的物理结果。

**已确认根因仅限于软件选错时间轴。** 它是否足以解释 19–24 px 图像运动尚未检验；真实抓取失败的物理根因仍为 UNKNOWN。此修正没有辨识真实传感器延迟或 CAN 传输延迟。

## 前人是否解决过相近问题

直接相关的是 [Bi-JCR 论文 §III–IV](https://arxiv.org/html/2505.24819v1)：实验平台包含两台 AgileX Piper，研究 RGB 图像与末端位姿的联合相机标定和场景重建。读过实际公式和代码，而非仅 README。它把视觉相机位姿与机器人相对位姿组成 AX=XB，求旋转、平移及视觉尺度；无需把深度文件当成真机观测。

核对的上游版本为 `412483e7b31f20342325f3d85a2a913e58547737`，关键源码：

- [jcr_subroutine.py](https://github.com/tomtang502/bijcr/blob/412483e7b31f20342325f3d85a2a913e58547737/src/jcr/jcr_subroutine.py)：`pm_solver_with_scale(eef_poses, c2w_poses, ...)`；`compute_dual_arms(...)` 分别处理两臂后合并尺度。已将固定提交的文件与读取版本逐字比较一致。
- [scale_calib_helper.py](https://github.com/tomtang502/bijcr/blob/412483e7b31f20342325f3d85a2a913e58547737/src/jcr/scale_calib_helper.py)：`compute_A_B_Rx_tr` 与最后一个有效定义 `compute_cost_tr`，相对变换、SVD 和平移最小二乘。
- [dual_jcr.py](https://github.com/tomtang502/bijcr/blob/412483e7b31f20342325f3d85a2a913e58547737/src/jcr_sgd/dual_jcr.py)：`sgd_axxb`、`gjcr_sgd` 的优化接口；[jcr.py](https://github.com/tomtang502/bijcr/blob/412483e7b31f20342325f3d85a2a913e58547737/src/jcr/jcr.py) 连接视觉重建。

**可复用的是位姿约束和数值求解机制，不是直接启动整套双臂流程。** 当前三条任务记录左臂六关节范围均为零，无法从它们辨识左臂眼在手上外参。右臂需要用已有多轴素材，检查视觉对应、内参与运动激励；仅有较大的关节范围不证明可辨识。上游视觉重建依赖模型，尺度搜索默认 CUDA、20 万采样；本次未下载模型、安装框架或发起 GPU 作业。学习得到的点云不是实测深度。相机标定也不等于摩擦/接触参数辨识。

另已核对 [DREAM 原论文 §II–III](https://www.ri.cmu.edu/app/uploads/2020/03/dream_icra2020_final.pdf) 及其 [PnP 实现](https://github.com/NVlabs/DREAM/blob/master/dream/geometric_vision.py)：RGB 关键点、机器人 FK 与内参可用于相机位姿求解。但其现成网络不是 Piper 模型，论文验证使用的深度真值也不能迁移成我们的证据。因此不另训网络，优先复用现有 OpenCV 和本地对应点接口。相关辨识综述的参数可辨识性部分只用于核查“缺少力传感器是否意味着所有校准都不可能”；它不支持这种结论，见 [Lee 等 2024，§2.2–2.3、3.1–3.2、5.1](https://par.nsf.gov/servlets/purl/10530091)。不继续扩展无关文献清单。

## 修正研究判断与下一步

第六轮的“夹具必须移动小于 1 px”是那个测量方案的额外假设，不是所有 RGB 标定方法的前提。相对双指位移本来就抵消共同二维平移；旋转、透视与特征失效仍需处理。左指全窗口存活失败是真实的工具局限，但不能据此推导 RGB 标定无路可走。ER006 增加此限制，并撤去“未执行的拟合已被实验证明无效”的表述。

后续应围绕既有多轴 RGB 和反馈，适配成熟单臂手眼约束，先核查时间、内参、静态对应与运动条件。不要直接重复固定 ROI 的夹指全窗口跟踪，也不要把标称模型尺寸当作实测几何。这个方向已找到相同型号的前人实现和本地输入，不需要先重新采集真机动作。

本次实际交付是观测软件修正和输入审计，**尚未执行 RGB 手眼求解，未证明 MuJoCo 改善或采集成本下降**。Stage 2 仍未通过；NO-GO 仅针对“最终研究目标已经实现”的声明，不再解释成停止一切可推进工作的理由。六轮上限和失败记录保持不变。

复核命令：使用现有 MuJoCo Python 环境运行本目录 verify.py，以及 `python -m unittest discover -s tests`。本次档案核验约 0.137 s（不含文献、开发和文件审阅）；planner 调用 0，编排 Token/推理耗时未独立计量。所有原始数据、私人配置及原仿真源码留在本地。
