# Method and reuse boundary

The actual bottleneck is in `agent_loop.py`: a transport failure still receives an insertion-offset-only action contract, and the right-arm branch discards all old failure warnings. Existing native IK and retention diagnosis work independently but are not called by this Agent.

[ASPIRE §2.1–2.2](https://arxiv.org/html/2607.00272v1#S2.SS1) addresses primitive-level debugging: localize the failed call using its trace, test a targeted repair, and retain only verified reusable knowledge. We read the actual method and current [planning.py source](https://github.com/NVlabs/ASPIRE/blob/main/src/cap_harness/behavior/planning.py), particularly `solve_ik` and `_full_result_outcome`. The implementation maps the active arm, applies the supplied joint seed to the planner state, and reports planning status/attempts/time separately from returned trajectories. Its cuRobo/OmniGibson dependencies and robot adapter are not suitable for this Piper project; no framework or source is copied.

Reuse the project's `diagnose_retention`, `probe_transport_ik`, native PoseIK and complete collector. The opt-in `diagnose_then_repair` entry checks for earlier retention loss, otherwise reproduces the saved transport target and screens existing grasp-angle candidates numerically. The model then chooses one bounded native parameter or stops. A feasible static IK sample is not a successful motion or a verified skill. Old profile/embodiment failures are supplied as explicitly scoped warnings, not current facts or executable poses.

Both old and candidate routes use the same failed seed, actual Luna model, one model call and one complete simulation execution. Only the candidate receives the diagnostic interface and its numeric cost is included. This evaluates the combined harness change; it does not isolate tool information from the expanded parameter interface. Default policy remains unchanged pending full physical and independent validation. Neither route controls hardware.
