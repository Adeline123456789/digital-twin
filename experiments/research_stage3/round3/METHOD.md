# Stage3 round3: bounded planner context

The existing `ask()` starts a complete Codex session for one bounded JSON plan. `debug prompt-input` showed a large automatic skills instruction block; disabling `skills.include_instructions` reduced that configured diagnostic block from 26,297 to 2,814 serialized characters. Debug uses user config, unlike the actual planner's ignore-user-config invocation, so this is source localization rather than a claimed token count.

[Official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents the invocation override. Only that flag changes. The task, robot protocol, retrieved applicable experience, project rules, read-only sandbox and downstream bounded-action validator remain. Global settings, installed skills and credentials are not modified.

[Voyager §2.2](https://arxiv.org/html/2305.16291v2#S2.SS2) addresses growing embodied skill libraries through retrieval of relevant executable programs. We read [SkillManager.retrieve_skills source](https://github.com/MineDojo/Voyager/blob/main/voyager/agents/skill.py): it limits retrieval to available/top-k skills and retrieves matching code. This supports limiting context to relevant skills; it does not establish this Codex optimization's benefit. The existing robot retrieval already caps records at five, so no embedding database, Minecraft runtime or new framework is added. Generic desktop/research skill discovery is unnecessary for this bounded planner call, whereas robot evidence remains explicitly supplied.

Four actual calls are preregistered: Luna baseline/candidate and Astra candidate/baseline. Each receives the same failed execution and simulator precontact residual within its pair, with no supplied successful answer. Returned offsets are validated and executed once through the unchanged original simulator and verified inline recorder. This measures context overhead with physical task evidence, not new task-family learning or A/B/C/D capability transfer.
